# LegacyTerrain 0.10.0 write compatibility and selected-region map export

## Crash root cause confirmed from the supplied `mod.mcworld`

The modified world was compared with the original 0.10.0 world at the physical LevelDB-record level.

- Target chunk key: `00 00 00 00 FF FF FF FF 30` = chunk `(0,-1)` `LegacyTerrain` (`0x30`).
- Both before and after values are exactly 83,200 bytes.
- Only one byte in the `LegacyTerrain` payload changed: offset 25,668, from numeric block ID `3` (dirt) to `57` (diamond block).
- No metadata, SkyLight, BlockLight, HeightMap or biome/color bytes changed.
- In X-Z-Y LegacyTerrain order that byte is local `(12,68,8)`, i.e. world `(12,68,-8)`. The supplied modified record therefore corresponds to Y=68; the original Y=8 position is numeric ID 1 (stone).

The crash is caused by the database container rewrite, not the 83,200-byte terrain payload:

- Original 0.10.0 SSTable data blocks use compression ID `2` (zlib).
- SSTables generated by the previous MCBEEditor build use compression ID `4` (raw deflate).
- The bridge previously registered `ZlibCompressorRaw` as `compressors[0]`; leveldb-mcpe uses the first registered compressor for new table blocks, so opening/recovery/compaction of the old database rewrote old zlib tables as raw-deflate tables.
- Pocket Edition 0.10.x predates compression ID 4 and can crash when loading those rewritten tables.

### Fix

`BTLevelDBBridge.mm` now registers:

1. `ZlibCompressor` first, so all new SSTable blocks are written using legacy-compatible compression ID 2.
2. `ZlibCompressorRaw` second, so modern compression ID 4 tables remain readable.

This deliberately favors backward compatibility. Existing modern worlds remain readable and writable; new/compacted tables may use zlib instead of raw deflate.

A world that has already been rewritten into ID-4 SSTables (such as the supplied broken `mod.mcworld`) should not be used to validate the fix. Re-import the untouched 0.10.0 world and repeat the edit with the fixed build.

## Chunk-list semantics

`LegacyTerrain` is one physical LevelDB record covering 16×128×16 blocks. MCBEEditor internally exposes it as eight 16-high virtual slices so the rest of the editor can reuse the SubChunk editing pipeline.

The old list UI incorrectly counted those virtual slices as eight physical `SubChunk` records. The list now keeps the concepts separate:

- `subChunkCount` counts only real `0x2F SubChunkPrefix` records.
- `hasLegacyTerrain` records the presence of physical `0x30 LegacyTerrain`.
- Legacy chunks display `LegacyTerrain 1（8 虚拟切片）` rather than `SubChunk 8`.
- Terrain-presence checks use `hasTerrain`, so old chunks are still included by map export, spread, commands and generated-chunk detection.

## Selected-region map image export

When frame-selection mode has an active region, `导出地图图片` now offers and defaults to `当前框选区域`.

- The renderer covers all chunks intersecting the selected block rectangle.
- Existing map mode, grid option and optional entity/block-entity/HardcodedSpawners/village/spawn layers are retained.
- The composed image is cropped to the exact selected X/Z block boundaries, including non-chunk-aligned selections.
- Without an active selection the option is hidden and the existing `当前地图区域` / `当前维度全部已加载区域` choices remain unchanged.

## Regression coverage

`Scripts/test_legacy_zlib_and_selection_export.sh` verifies:

- zlib is the first write compressor and raw deflate remains registered for reading;
- LegacyTerrain virtual slices are not counted as physical SubChunks;
- the chunk summary exposes LegacyTerrain explicitly;
- selected-region export is only offered with an active selection and uses exact cropping.

The complete existing core test suite was also run through its remaining sections after these changes, including LegacyTerrain/SubChunk v0-v9 persistence, block editing, region editing/copying, chunk regeneration, biome/HardcodedSpawners, ticking areas and command execution.
